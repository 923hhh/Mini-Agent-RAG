# DomainRAG 检索优化执行方案

> 文档类型：研发执行文档  
> 版本时间：2026-05-12  
> 关联评测：[`data/eval/domain/domainrag_full_local_eval.json`](/e:/南京航空航天大学/aaa大创/智能体案例/Mini-Agent-RAG2/data/eval/domain/domainrag_full_local_eval.json)

---

## 1. 摘要

当前 RAG 的主要问题不是模型完全不会答，而是检索目标仍偏向“单段最像”，还没有真正对齐开放场景下更重要的四个目标：多证据覆盖、时间状态正确、重复页抑制、证据可答性保真。

因此，这份文档不再停留在“问题诊断 + 优化方向”，而是把已经明确的 bad case、代码侧根因、执行顺序、回归方式和验收口径收束成一份可直接推进的研发执行文档。后续优化默认按以下优先级推进：

1. `P0` 多文档覆盖
2. `P1` 时间敏感排序
3. `P2` 去重与前排排序
4. `P3` 上下文组织与证据保真

先做 `P0/P1` 的原因很明确：当前系统在 `CRUD 3QA` 这种闭环场景已经可以做到稳定命中，真正暴露短板的是 `DomainRAG` 里的比较类、多证据类、时间敏感类和开放页面重复干扰。后续优化应优先修正检索目标和排序目标，而不是先把问题笼统归因为“模型不够强”。

## 2. 当前基线与优先级依据

### 2.1 总体基线

| 指标 | 当前值 |
| ---- | ------ |
| Recall@5 | 0.4877 |
| MRR | 0.4200 |
| NDCG@5 | 0.4032 |
| Hit@1 | 0.3842 |
| Hit@10 | 0.5123 |

### 2.2 分任务基线

| 任务类型 | Recall@5 | MRR | NDCG@5 | 补充观察 |
| ---- | ---- | ---- | ---- | ---- |
| extractive_qa | 0.4889 | 0.4019 | 0.4231 | 前排错排明显 |
| multi-doc_qa | 0.4375 | 0.3767 | 0.2501 | All Positive Covered@10 = 0.1250 |
| time-sensitive_qa | 0.5231 | 0.4769 | 0.4886 | 时间约束未稳定进入排序 |

### 2.3 生成侧补充判断

生成侧最新自动评测中，`Context Recall=0.4287`、`Faithfulness=0.5823`。这说明问题不只在“有没有检到”，还在“送给模型的上下文是否足够可用”。但从当前 bad case 看，生成问题更多是在放大前面检索与证据组织的偏差，因此执行顺序上仍应先修 `P0/P1/P2`，再做 `P3`。

### 2.4 为什么按这个优先级做

- `multi-doc_qa` 的 `All Positive Covered@10` 只有 `0.1250`，说明多证据题的主要矛盾是覆盖目标设错，不是单纯排序略差。
- `time-sensitive_qa` 的典型坏例不是“完全召回不到”，而是“年份相近但不答题”的页面排在前面，说明问题集中在排序强特征不足。
- `extractive_qa` 的大量失败表现为重复热点页霸榜，说明通用去重与前排排序仍需补课。
- `P3` 确实重要，但它建立在“前面已经把证据找对并排对”的前提之上，因此应该放在后面做放大收益。

## 3. 重点 bad case 诊断

这一部分统一按“典型坏例 -> 当前现象 -> 代码侧根因 -> 直接改法”组织，避免后续实施时还要再做一次问题归因。

### 3.1 `multi-doc_qa`：多证据题的目标仍是“单段最像”

**典型坏例**  
“数学与应用数学专业与数据计算及应用专业在人才培养的共同目标和独特特点是什么？”

**当前现象**  
- gold 证据并不总是完全召回失败，但前排结果经常不能把多个关键证据同时凑齐。
- 即使命中相关材料，也容易混入“市场营销”“艺术类招生简章”等主题接近但不可答的噪声页。
- 当前指标里 `All Positive Covered@10` 很低，说明问题不只是首条排序偏差，而是前排候选整体覆盖不足。

**代码侧根因**  
- 比较类 query 当前在 `query_rewrite_service` 里会直接返回原 query，不做多查询拆分，也不做子意图展开。
- 当前 rerank 和最终候选选择仍主要奖励“单段最相关”，还没有 coverage-aware 目标。
- 当前 diversity 逻辑主要做 family/doc 去重，不保证“对象 A + 对象 B + 共同点/差异点”都能进前排。
- prompt context 默认条数和 snippet 长度偏保守，会进一步放大“证据不全”的问题。

**直接改法**  
- 为比较类 query 引入可控的子查询拆分，不再只保留原始问句。
- 在 rerank / final select 中加入 coverage bonus 和 doc-level diversity，让互补证据更容易共存。
- 在 comparative query 的上下文组织里优先保留“共同点 / 对象 A / 对象 B / 差异点”所需证据，而不是继续按单段相似度挤压。

### 3.2 `time-sensitive_qa`：时间词进了 query，但没变成足够强的排序约束

**典型坏例**  
“中国人民大学的校长是谁？”

**当前现象**  
- 这类问题常能带上年份或“当前/现任”等约束进入 query。
- 但前排仍容易出现“2023 年艺术类招生简章”之类年份相近、词面相关、实际不答题的页面。
- 典型失败不是完全没有相关页面，而是伪相关结果在排序上压过了真正能回答“当前职位”的证据。

**代码侧根因**  
- 时间约束虽然能进入 query rewrite 或评测 query 构造，但在排序里的增益仍偏弱。
- 当前 temporal adjustment 更像 bonus/penalty，而不是对“实体 + 角色 + 时间”同时匹配的强约束。
- “现任/当前职位类问题”仍缺少足够明确的角色词与实体词联合排序信号。

**直接改法**  
- 强化“当前/现任/截至某年/谁是校长”等时间敏感和职位类问句识别。
- 在 heuristic rerank 里提高日期、角色词、标题命中、实体精确匹配的权重。
- 对时间相近但不具备职位答案句的候选增加惩罚，压制“看起来相关但不答题”的页面。

### 3.3 `extractive_qa`：重复热点页霸榜，真正答案页排不进来

**典型坏例**  
“中国人民大学中法学院用哪三个语言进行教学？”

**当前现象**  
- 正确答案页不是完全不存在，但前排经常被同标题、同栏目、同热点专题的多个变体页面占满。
- 结果表现为 `Hit@1` 和 `MRR` 偏低，且很多 extractive 题看起来像“检索到了同域材料”，其实没有命中真正答案页。
- 在人工 bad case 分桶里，这类问题也经常体现为 `low_rank` 或重复壳页干扰。

**代码侧根因**  
- 当前 family/sample group 聚合和加权逻辑，在某些情况下会进一步放大重复页面前排占位。
- 同源 URL、多锚点页面、标题壳页之间的抑制仍不够强。
- 答案句级信号还不足以持续压过热点页的词面相关性。

**直接改法**  
- 引入标题 / URL / family 归一化去重，降低同源变体重复占位。
- 调整 sample-group 相关增益，避免重复簇被继续强化。
- 在前排排序中提高答案句级命中、实体精确匹配和标题对齐特征的权重。

## 4. 分阶段执行方案

后续实现默认按阶段推进。每个阶段只解决一类主矛盾，不把结构重构、算法变化和评测口径调整混在同一轮里。

### 阶段一：`P0` 多文档覆盖

**目标**  
先把 `multi-doc_qa` 从“单段最像”拉到“关键证据尽量覆盖全”。

**本阶段只解决什么**  
- 比较类、多对象、多子问场景下的前排证据覆盖不足
- 互补证据被单主题候选挤压的问题

**暂不解决什么**  
- 不在这一阶段处理时间敏感排序
- 不在这一阶段主攻重复热点页霸榜
- 不在这一阶段大改生成 prompt 或答案模板

**实现动作**  
- 将比较类 query 从“只保留原 query”改为可控的子查询拆分。
- 在 rerank 中增加 coverage bonus，不再只奖励单段相关性。
- 在 final select 中加入 doc-level diversity，减少同主题候选重复占位。
- 允许比较题保留互补证据，避免过早去重导致其中一侧信息被裁掉。

**影响模块**  
- `query_rewrite_service`
- 候选重排与多样化逻辑
- context 组织逻辑

**回归方式**  
- 固定回放多专业比较类 bad case
- 跑 `DomainRAG` 全量本地评测并观察分任务指标
- 同步确认 `CRUD 3QA` 不回退

**验收指标**  
- `multi-doc_qa All Positive Covered@10`
- `multi-doc_qa NDCG@5`
- 比较类典型 bad-case replay 的完整性

### 阶段二：`P1` 时间敏感排序

**目标**  
把“年份相近但不答题”的伪相关页面压下去。

**本阶段只解决什么**  
- 时间敏感题里“时间词保留了，但排序没有对齐当前状态”的问题
- 现任/当前职位类问题的角色匹配不足

**暂不解决什么**  
- 不在这一阶段处理多文档 coverage 的进一步生成组织
- 不在这一阶段系统性处理重复热点页
- 不引入新的对外接口或新的评测口径

**实现动作**  
- 强化“当前/现任/截至某年/职位类问句”的识别规则和 query profile。
- 把实体、角色词、日期、标题命中增强为更强的排序特征。
- 对时间匹配但角色不匹配、或没有答案句支撑的页面增加惩罚。

**影响模块**  
- query profile
- temporal candidate adjustment
- heuristic rerank

**回归方式**  
- 固定回放“校长是谁”类 bad case
- 跑 `DomainRAG` 全量本地评测并重点观察 `time-sensitive_qa`
- 同步确认 `CRUD 3QA` 不回退

**验收指标**  
- `time-sensitive_qa MRR`
- `time-sensitive_qa Hit@5`
- 校长类 bad-case replay 是否从伪相关前排回到正确证据前排

### 阶段三：`P2` 去重与前排排序

**目标**  
解决重复热点页霸榜，抬高真正答案页的 `Top1` 命中率。

**本阶段只解决什么**  
- 同标题、同源 URL、多锚点页面反复占位
- 重复簇因 sample-group/family 逻辑被继续强化的问题

**暂不解决什么**  
- 不在这一阶段引入新的长文检索形态
- 不在这一阶段主攻比较类上下文组织
- 不调整生成侧评价指标口径

**实现动作**  
- 做标题 / URL / family 归一化去重。
- 控制同源变体页面在前排的占比，降低一个热点专题占满 `TopK` 的概率。
- 调整 sample-group 相关增益，避免重复簇持续获得额外排序优势。

**影响模块**  
- family/sample group 选择逻辑
- rerank 前后去重逻辑

**回归方式**  
- 固定回放“三语教学”类 extractive bad case
- 跑 `DomainRAG` 全量本地评测并重点观察 `extractive_qa`
- 同步确认 `CRUD 3QA` 不回退

**验收指标**  
- `extractive_qa Hit@1`
- `extractive_qa MRR`
- 三语教学类 bad-case replay 是否摆脱热点页霸榜

### 阶段四：`P3` 上下文组织与证据保真

**目标**  
减少“检索命中了，但最终答残了”的假失败。

**本阶段只解决什么**  
- prompt context 条数、裁切长度和组织顺序导致的证据利用不足
- 比较题和多证据题中“证据到了，但答案没整合完整”的问题

**暂不解决什么**  
- 不在这一阶段继续大改召回主链路
- 不在这一阶段更换主模型或评测框架
- 不在这一阶段引入新的外部接口

**实现动作**  
- comparative query 放宽 prompt 去重，让互补证据能共存。
- 调整 reference 条数与 snippet 长度策略，减少过度压缩。
- 按“共同点 / 差异点 / 对象 A / 对象 B”保序组织证据，提高最终可答性。

**影响模块**  
- `context_build_service`
- `evidence_packing_service`

**回归方式**  
- 固定回放多文档比较题的完整性
- 跑 `DomainRAG` 全量本地评测
- 在这一阶段开始补看生成侧自动评测

**验收指标**  
- bad-case replay 的回答完整性
- `Context Recall`
- `Faithfulness`

## 5. 实施纪律

这一部分与现有项目守则对齐，防止执行过程中再次把问题混层。

### 5.1 每阶段只改一类主矛盾

- 不在同一轮同时大改结构、算法、评测口径
- 不把“主链路重构”和“指标优化”混成一次提交目标
- 若本轮目标是 `P0`，就不同时夹带 `P2/P3` 的大改

### 5.2 不继续让主链路热点文件膨胀

后续实现必须遵守：

- 不继续让 `app/retrievers/local_kb.py` 膨胀
- 不继续让 `app/chains/rag.py` 承接更多系统级职责
- 新策略优先沉到 retrieval services，而不是直接堆在薄入口或 chain 里

### 5.3 query 判断统一收口

- 时间敏感、比较类、答案窗口类等 query 识别必须继续收口在 retrieval services
- 禁止在 API、retriever 入口、chain 中再复制一套关键词特判

### 5.4 新策略必须可开关、可回归、可旁路

- 每个阶段新增策略都应具备可单独启停能力
- 关闭扩展逻辑时，主文本链路不应被污染
- 每轮都必须能用固定 bad-case replay 和 full eval 验证收益与副作用

### 5.5 每阶段结束的固定收口动作

每个阶段完成后，默认按以下顺序收口：

1. 先跑 bad-case replay
2. 再跑 `DomainRAG` 全量本地评测
3. 最后确认 `CRUD 3QA` 指标不回退

只有通过这三步，才进入下一阶段。

## 6. 验收与回归口径

### 6.1 本轮文档整理不变更的边界

- 不新增对外 API
- 不调整现有 route、schema 或脚本入口口径
- 可以点名后续可能影响的内部模块，但不在文档里提前承诺新的配置格式

### 6.2 验收指标

| 评测对象 | 当前值 | 验收目标 |
| ---- | ---- | ---- |
| Domain 总体 Recall@5 | 0.4877 | >= 0.55 |
| Domain 总体 MRR | 0.4200 | >= 0.48 |
| multi-doc_qa All Positive Covered@10 | 0.1250 | >= 0.25 |
| multi-doc_qa NDCG@5 | 0.2501 | >= 0.35 |
| time-sensitive_qa MRR | 0.4769 | >= 0.55 |
| extractive_qa Hit@1 | 0.3667 | 至少提升一个可观台阶 |
| CRUD Recall@5 / MRR | 1.0 / 1.0 | 不回退 |

### 6.3 每阶段最低验证集

**bad-case replay**

- 多文档比较题：数学与应用数学 vs 数据计算及应用
- 时间敏感题：中国人民大学校长是谁
- extractive 题：中法学院三语教学

**full eval**

- `DomainRAG` 全量本地评测，必须看分任务指标，不只看总均值

**guard rail**

- `CRUD 3QA` 本地闭环指标不回退

**generation check**

- 仅在 `P3` 后重点关注 `Context Recall` 与 `Faithfulness`

## 7. 结论

当前 `DomainRAG` 的核心矛盾已经比较清楚：不是系统完全检索不到，而是开放场景下的目标函数仍偏向“单段最像”，还没有真正对齐“多证据覆盖”“时间状态正确”“重复页抑制”“证据可答性保真”这几个更接近真实问答效果的目标。

因此，后续优化的正确路径不是继续泛化地加模块或单纯换更强模型，而是按阶段把检索目标和排序目标纠正过来。只要 `P0` 到 `P3` 能按顺序推进并形成稳定回归闭环，当前 Domain 本地知识库指标仍有比较明确的提升空间。
