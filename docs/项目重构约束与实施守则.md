# 项目重构约束与实施守则

> 文档类型：项目治理与实施约束  
> 版本时间：2026-04-29  
> 适用范围：Mini-Agent-RAG 全项目，后端 `app/` 为重点约束区域

---

## 1. 总原则

本项目后续重构必须遵守以下总原则：

1. 小步重构，阶段收口，不做一次性全盘翻修
2. 行为不变优先于结构变美
3. 路径清晰优先于抽象华丽
4. 主链路稳定优先于实验能力扩展

这些原则的目的不是保守不动，而是防止在主链路尚未建立稳定回归前，为了结构整洁而引入不可控回归。

---

## 2. 后端必守约束

### 2.1 主链路文件停止继续膨胀

以下文件被视为主链路热点文件：

- `app/retrievers/local_kb.py`
- `app/chains/rag.py`

从本守则生效开始：

- 新逻辑不得继续直接堆进以上文件
- 以上文件只能做减负、拆分和入口收缩
- 若必须临时调整，也只能做小范围修复，不能继续增加系统级职责

### 2.2 query 判断统一收口

所有 query 类型识别逻辑必须集中管理。  
禁止以下行为：

- 多处复制“时间敏感”“比较类”“timeseries 相关”判断
- 在 retriever、chain、API 层各自再造一套关键词规则

允许的行为：

- 将 query 类型识别集中到统一 service
- 由统一识别结果驱动后续召回、重排和上下文组织

### 2.3 候选召回、候选打分、上下文拼接、答案审校不得混层

必须遵守以下边界：

- `api` 层不承载业务策略
- `retrievers` 保持薄入口
- `chains` 保持编排职责
- `services` 承担可复用计算

明确禁止：

- 在 API 路由中堆 query 分析或排序逻辑
- 在 retriever 中继续新增大段 context packing 逻辑
- 在 chain 中继续新增大量候选打分逻辑

### 2.4 扩展能力必须可开关、可旁路、可单独测试

timeseries 等扩展能力当前已经接入主链路，因此后续必须满足：

- 功能开关能真正控制行为
- 扩展能力关闭时，主文本链路不应被污染
- 扩展能力必须可单独回归

禁止：

- 让实验能力以散点特判形式永久留在主流程文件中
- 让功能开关只控制部分分支、却保留隐式副作用

---

## 3. 兼容性约束

### 3.1 不得无计划修改稳定入口

以下对象默认视为稳定入口：

- 现有 API 路由
- 关键 schema
- 常用脚本命令

若必须调整，必须满足至少一项：

- 保留兼容层
- 提供迁移说明
- 提供过渡期双入口

### 3.2 兼容壳只能减负，不能继续长肉

`app/loaders/documents.py` 当前已经是兼容转发层。  
后续规则如下：

- 可以逐步减少其职责
- 可以让调用方迁移到更明确的入口
- 不允许在兼容壳里继续新增核心逻辑

### 3.3 不删仍被引用的兼容入口

禁止为了“目录看起来更干净”而直接删除仍被正式代码引用的兼容文件。  
正确顺序必须是：

1. 先迁移调用方
2. 再缩减兼容层
3. 最后删除兼容层

---

## 4. 目录与产物治理约束

### 4.1 `scripts/` 治理规则

`scripts/` 必须区分以下三类：

- 正式保留脚本：主流程可重复运行
- 归档脚本：阶段性曾使用，但不再作为正式入口
- 一次性分析脚本：只用于某次诊断或报告生成

禁止：

- 无说明地长期保留一次性分析脚本在主脚本层
- 让 README 指向不稳定或历史脚本

### 4.2 `data/eval/` 治理规则

`data/eval/` 必须区分：

- 最终结果
- 分片中间产物
- 分析材料
- 历史归档

当前 `data/eval/crud/` 与 `data/eval/phase0/` 已经出现多版本、分片和历史结果并存现象，因此后续必须禁止：

- “总结果 + 分片结果 + 旧版结果”长期并列无说明
- 报告口径不清却把多个版本都留在同层

### 4.3 文档治理规则

文档必须按用途分层：

- 对外说明
- 技术说明
- 研发路线
- 过程留档

禁止继续把所有说明都平铺在同一层级而无分类意图。

---

## 5. 重构禁区

以下行为在重构期间视为禁区：

1. 不在同一阶段同时改结构、改算法、改指标口径
2. 不为了一次性“收拾干净”而删掉仍被引用的兼容入口
3. 不在未建立回归基线时拆主链路
4. 不把临时实验逻辑长期留在主流程文件里
5. 不在主链路重构阶段顺手做 UI 大改、模型替换或评测体系更换

这些禁区的目的，是避免把“结构问题”和“行为变化”混成同一类问题，导致回归定位失效。

---

## 6. 评测与回归纪律

### 6.1 每轮重构的最低回归要求

每轮结构重构至少保留以下回归：

- 主 API smoke test
- 知识库重建 smoke test
- Domain 检索回归
- CRUD 闭环稳定性回归

### 6.2 结构重构默认不应带来系统性指标回退

若某轮只做结构重构，则默认：

- 指标不应出现系统性回退
- 若有局部波动，必须能解释为非目标变化

### 6.3 行为变化必须说明原因

若某轮行为变化是预期的，则提交说明必须明确：

- 为何变化
- 变化影响哪一层
- 用什么回归验证
- 对 Domain / CRUD 哪些口径有预期影响

禁止：

- 只说“重构了代码，所以结果略有变化”
- 不区分结构影响和算法影响

---

## 7. 当前项目必须正视的事实

本守则不是通用规范，必须立足当前仓库事实执行。以下事实应视为后续治理前提：

- `app/retrievers/local_kb.py` 是当前最大的主链路热点文件
- `app/chains/rag.py` 是 RAG 编排与特判逻辑集中区
- `app/services/README.md` 已给出一版 service category layout，但尚未完全落到职责边界
- `app/loaders/documents.py` 当前是兼容转发层
- `scripts/` 下存在多支一次性分析脚本
- `data/eval/crud/` 与 `data/eval/phase0/` 当前存在多版本、分片和历史结果并存现象

后续所有重构动作都必须围绕这些真实问题展开，而不是套用外部模板。

---

## 8. 结论

这份守则的核心目的，是让项目重构从“想到哪里改哪里”转成“按边界改、按阶段改、按回归改”。  
后续任何结构调整，只要违反以下任一项，都应被视为越界：

- 继续让主链路热点文件增长
- 混淆 retriever、chain、service 层职责
- 未建立基线就拆主流程
- 在结构重构中夹带算法变化
- 不治理脚本和评测产物生命周期

只有先守住这些硬约束，后面的结构优化、能力扩展和评测结论才会越来越可信。
