## 一、项目概况

本项目名称为“基于多智能体的故障检测系统”，面向复杂设备故障检测、检修辅助与根因分析场景，围绕“领域知识库 + RAG 检索增强生成 + 多智能体协同”开展研究。项目目标是构建一个能够理解故障现象、检索相关知识、分析可能原因、生成处置建议并展示依据来源的智能化辅助原型系统，为设备检修和故障诊断过程提供知识支撑与决策参考。

当前阶段，团队已完成项目技术路线论证、本地知识库问答原型建设、RAG 检索增强流程验证、故障检修业务原型开发和智能体链路初步验证等工作。现有 Mini-Agent-RAG 工程主要作为项目的 RAG 技术底座，用于验证文档入库、混合检索、证据重排、上下文组织、答案生成和评测分析等核心能力。后续将在该技术底座上进一步接入故障资料、设备文档、检修记录样例和典型故障案例，形成面向故障检测场景的领域知识库和多智能体诊断流程。

## 三、研究方案与技术路线

### 3.1 总体研究思路

项目按照“知识基础建设—检索与问答能力验证—智能体协同设计—业务原型集成—实验评估优化”的路线逐步推进。

第一，构建设备故障领域知识库。项目将整理公开故障数据集、设备资料、检修记录样例、故障案例和维修 SOP 文档等资料，对文本进行清洗、切分、结构化整理和向量化索引构建，逐步形成包含故障现象、可能原因、检测方法、检修步骤和处理建议的知识库。

第二，完善 RAG 检索增强生成能力。系统针对用户输入的故障现象或检修问题，先进行问题理解，再从知识库中检索相关知识片段，通过重排、证据组织和上下文构建，为大模型生成诊断结果提供依据。输出内容包括可能故障原因、定位思路、处理建议和相关证据来源。

第三，探索多智能体协同诊断流程。项目拟设计感知智能体、规划智能体、诊断智能体和校验智能体等角色。其中，感知智能体负责解析故障现象和检修输入；规划智能体负责任务拆解和诊断流程组织；诊断智能体负责结合检索证据生成原因分析和处理建议；校验智能体负责检查诊断结果的依据性、完整性和一致性。

第四，推进故障诊断与检修业务原型集成。后续将在现有业务原型基础上，实现故障输入、知识检索、诊断建议、证据展示、任务生成和案例沉淀等模块联动，形成可演示的故障检测与检修辅助流程。

第五，开展实验验证与效果评估。项目将结合公开数据集、领域知识文档和人工构造的典型业务样例，从检索质量、诊断相关性、回答依据性、结果可解释性和系统响应效率等方面进行评估，并与普通大模型问答或单一检索方式进行对比。

### 3.2 当前原型系统架构

当前 Mini-Agent-RAG 工程采用 FastAPI + Streamlit 架构，作为项目当前阶段的知识库问答和 RAG 能力验证平台。

| 层级 | 技术或模块 | 主要职责 |
| ---- | ---------- | -------- |
| 前端交互层 | Streamlit | 知识库管理、RAG 对话、Agent 对话和过程展示 |
| 后端服务层 | FastAPI | 提供知识库、问答、Agent 等接口 |
| 检索增强层 | BGE-M3、BM25、RRF、Reranker | 文档召回、候选融合、证据重排 |
| 模型生成层 | DeepSeek-Chat | 根据检索证据生成回答或诊断建议 |
| 评测诊断层 | 自动评测脚本、RAGAS、人工分析 | 评估检索与生成质量，定位问题原因 |

### 3.3 RAG 主流程

当前已验证的 RAG 主链路如下：

```text
用户问题 / 故障描述
  -> 查询理解与查询改写
  -> Dense + BM25 混合检索
  -> RRF 候选融合
  -> 启发式重排
  -> 模型重排
  -> 句级索引与 Small-to-Big 上下文扩展
  -> 证据组织
  -> 大模型生成
  -> 完备性与事实性检查
  -> 回答 / 诊断建议输出
```

![RAG 主链路流程图](./img/rag.png)

该链路后续可迁移到故障检测场景：将普通文档问答中的“问题”替换为“故障现象或检修问题”，将高校文档知识库替换为故障案例、设备手册和检修记录知识库，即可支撑故障知识检索、根因分析和处理建议生成。

## 四、关键技术与创新特色

### 4.1 多智能体协同诊断思路

项目拟将故障检测与诊断过程拆分为感知、规划、诊断、校验等多个功能角色，由不同智能体分别承担故障信息理解、任务拆解、原因分析、处理建议生成和结果检查等任务。相比单一大模型直接生成诊断结论的方式，该思路更强调任务分工、流程协同和结果可解释性，有助于提升复杂故障分析过程的条理性与可靠性。

### 4.2 RAG 与领域知识库结合

项目不单纯依赖大模型参数知识，而是构建面向设备故障检测与检修场景的领域知识库，将故障案例、设备资料、检修记录、维修经验和处理措施等内容纳入检索范围。系统在生成故障原因分析和处理建议时，可结合检索到的相关证据进行回答，从而提高诊断输出的依据性、可靠性和可解释性。

### 4.3 混合检索与证据重排

当前原型已实现 Dense 向量检索与 BM25 关键词检索融合，兼顾语义匹配和专业术语精确匹配。系统还通过 RRF 候选融合、启发式重排和模型重排提升证据排序质量，为后续故障诊断场景中的设备编号、故障代码、部件名称和现象描述检索提供技术基础。

### 4.4 面向业务场景的原型验证

项目不仅关注算法流程，也面向设备检修业务中的故障上报、知识检索、诊断分析、处理建议生成和案例沉淀等环节开展原型设计。当前已初步形成检修业务系统原型，为后续系统演示和业务样例验证提供支撑。

## 五、Agent 链路验证进展

本阶段已在现有工程中完成单智能体多步工具调用的初步验证。当前系统能够根据用户问题规划工具调用步骤，执行本地知识库搜索、计算、获取当前时间等工具，并将工具结果综合成最终回答。

已完成的能力包括：

1. **多步工具调用主链路**：支持“Agent 规划 -> 工具调用 -> 结果观察 -> 综合回答”的闭环。
2. **有限任务调度能力**：能够在 `search_local_knowledge`、`calculate`、`current_time` 等工具之间进行简单调度。
3. **流式事件返回**：后端支持 Agent 流式输出，前端可以展示工具调用记录和中间步骤。
4. **会话记忆接口**：已接入 `session_id` 维度的记忆读写，为多轮任务处理保留扩展空间。
5. **诊断信息展示**：能够展示部分检索和推理过程，有利于后续演示和调试。

需要说明的是，当前完成的是单智能体多步执行和工具闭环验证，还不是完整的多智能体协同系统。后续将围绕感知智能体、规划智能体、诊断智能体和校验智能体进一步细化角色分工与协作流程。

## 六、阶段性实验与评测结果

当前实验主要基于 Mini-Agent-RAG 技术底座开展，用于验证 RAG 链路本身的有效性。虽然评测数据暂未完全切换为故障检测领域数据，但相关结果能够说明当前检索增强、重排和生成评测流程已经具备可用基础，后续可迁移到故障知识库中继续验证。

### 6.1 小样本检索优化效果

在 Domain 100 小样本稳定版评测中，系统从初始基线优化到当前稳定版后，检索指标明显提升：

| 数据集 | 版本 | Recall@5 | MRR | NDCG@5 |
| ------ | ---- | -------- | --- | ------ |
| CRUD 100 | 闭环基线 | 1.0000 | 1.0000 | 1.0000 |
| Domain 100 | 初始基线 | 0.8000 | 0.6262 | 0.6236 |
| Domain 100 | 当前稳定版 | **0.8900** | **0.7340** | **0.7379** |

其中，Domain 100 的 MRR 提升 `+0.1078`，NDCG@5 提升 `+0.1143`，说明混合检索、重排和上下文组织优化对开放文档问答场景有效。

### 6.2 混合检索效果

Dense only、BM25 only 和 Hybrid 三种方式对比如下：

| 方法 | Recall@5 | MRR | NDCG@5 |
| ---- | -------- | --- | ------ |
| Dense only | 0.8500 | 0.6583 | 0.6604 |
| BM25 only | 0.8500 | 0.6905 | 0.6930 |
| Hybrid | **0.8900** | **0.7318** | **0.7265** |

实验结果表明，单纯依赖语义向量检索或关键词检索都存在局限，二者融合后可以提高召回稳定性和前排排序质量。这一点对故障检测场景也具有参考价值，因为故障诊断问题往往同时包含自然语言现象描述和设备型号、部件名称、故障代码等关键词。

### 6.3 Reranker 组件效果

重排模型对比结果如下：

| 指标 | bge-reranker-base | bge-reranker-v2-m3 | 增量 |
| ---- | ----------------- | ------------------ | ---- |
| Recall@5 | 0.8700 | 0.8900 | +0.0200 |
| MRR | 0.7298 | 0.7418 | +0.0120 |
| NDCG@5 | 0.7317 | 0.7482 | +0.0165 |
| Top1 Hit | 0.6600 | 0.6700 | +0.0100 |

结果说明，模型重排能够进一步改善候选证据顺序。后续迁移到故障检测场景时，可将重排重点放在故障现象、设备部件、可能原因和处理措施之间的相关性判断上。

### 6.4 全量本地知识库评测

在 DomainRAG 全量语料本地评测中，系统覆盖 346 条样本，结果如下：

| 数据集 | 样本口径 | Recall@5 | MRR | NDCG@5 | Hit@1 | Hit@10 |
| ------ | -------- | -------- | --- | ------ | ----- | ------ |
| DomainRAG Local KB | 346 条全量样本 | 0.5145 | 0.4415 | 0.4378 | 0.4017 | 0.5520 |

这组结果说明，在全量开放语料下，系统难度明显高于小样本稳定版。当前短板主要集中在多文档证据覆盖和时间敏感信息排序上。该结论也提示后续故障检测场景需要重点关注跨文档故障证据整合、维修步骤关联和时序检修记录利用。

### 6.5 生成质量评测

在 Domain100 最新 100 条自动评测中，生成侧结果如下：

| 数据集 | 样本口径 | Context Recall | Faithfulness | Factual Correctness | Answer Relevance |
| ------ | -------- | -------------- | ------------ | ------------------- | ---------------- |
| Domain100 | 100 条小样本自动评测 | 0.4287 | 0.5823 | null | null |

该结果说明，当前生成阶段仍存在有效证据利用率偏低和回答忠实性不足的问题。后续在故障诊断任务中，需要进一步强化证据覆盖检查、诊断结论引用依据和不确定信息的保守表达，避免无依据生成错误诊断建议。

### 6.6 人工 Bad Case 分析

在 Phase 0 人工评测的 50 条样本中，错误类型分布如下：

| 类型 | 数量 | 占比 | 含义 |
| ---- | ---- | ---- | ---- |
| cross_passage | 18 | 36% | 答案依赖跨段信息整合 |
| chunk_noise | 12 | 24% | 命中但文本块未直接承载答案 |
| low_rank | 12 | 24% | 命中但排不到 Top1 |
| missed_recall | 6 | 12% | 完全未召回 |
| passed | 2 | 4% | 完全正确 |

关键指标为：`Recall@20=0.88`，`MRR@10=0.67`，`Top1 accuracy=0.58`。这说明系统当前的主要矛盾已经从“完全找不到证据”逐渐转向“证据块不够准确、排序不够靠前、跨段信息整合不足”。这些问题与故障诊断场景高度相关，因为故障根因分析通常需要综合故障现象、设备结构、历史案例和处理步骤等多类证据。

## 七、关键问题与解决思路

### 7.1 故障数据来源分散，知识表达不统一

故障检测相关资料通常来自设备手册、检修记录、故障案例、维修 SOP 和公开数据集，格式与表达方式不一致。后续将采用统一的知识条目模板，对故障模式、设备部件、观测现象、可能原因和处置措施等字段进行结构化整理，逐步形成标准化故障知识库。

### 7.2 大模型生成诊断建议可能缺乏依据

大模型直接生成故障原因和处理建议时，可能出现事实性错误或无依据扩写。项目将通过 RAG 技术在生成前先召回相关故障案例和资料片段，并要求输出中保留证据来源、原文摘要或知识条目编号，提高诊断输出的可信度和可解释性。

### 7.3 多智能体协同流程实现复杂

多智能体协同涉及角色划分、任务拆解、状态传递和结果校验，工程复杂度较高。当前阶段先采用轻量化协同结构，验证“故障输入解析—知识检索—综合诊断—结果校验”的基本闭环，后续再逐步细化智能体角色和协同策略。

### 7.4 故障根因分析效果难以客观验证

根因分析结果往往不只有唯一答案，评估难度较高。后续将优先选用带有故障标签、现象描述或原因说明的真实案例和公开数据集，结合部分人工标注，建立小型标准评估集，并通过 Top-k 命中率、MRR、回答依据性和专家判断等方式综合评估系统效果。

## 八、阶段成果总结

本阶段项目取得的主要成果如下：

1. **完成项目方向与技术路线论证**  
   团队已明确以“领域知识库 + RAG 检索增强 + 多智能体协同”为核心路线，围绕故障检测与根因分析开展后续研究。

2. **完成本地知识库问答原型建设**  
   当前 Mini-Agent-RAG 工程已跑通文档入库、混合检索、证据重排、上下文组织、答案生成和评测分析流程，为故障检测知识库建设提供技术底座。

3. **验证混合检索与重排优化有效性**  
   在阶段评测中，Domain 100 的 MRR 从 0.6262 提升到 0.7340，说明当前检索增强和重排优化方向有效。

4. **初步形成故障检修业务原型基础**  
   团队已围绕故障检修场景开展业务原型开发，形成知识检索、任务生成、案例管理和诊断辅助展示等基础模块。

5. **初步验证 Agent 多步工具调用链路**  
   系统已支持单智能体多步工具调用、流式步骤展示和会话记忆接口，为后续多智能体协同诊断流程提供工程基础。

6. **建立初步评测与问题诊断闭环**  
   项目已具备自动评测和人工 Bad Case 分析能力，可以从检索、排序、上下文组织和生成忠实性等角度定位问题。

## 九、存在问题

当前项目仍存在以下不足：

1. **故障领域知识库仍需完善**  
   当前 RAG 技术底座已经跑通，但故障资料、设备文档、检修记录和典型案例仍需继续整理、结构化和批量入库。

2. **多智能体协同仍处于初步验证阶段**  
   目前已完成单智能体多步工具调用和流程骨架验证，完整的感知、规划、诊断、校验多角色协同机制仍需继续设计与实现。

3. **生成结果的依据性和忠实性仍需提升**  
   当前评测显示系统在证据利用和回答忠实性方面仍有提升空间。故障诊断场景对输出可靠性要求更高，后续需要强化证据引用和结果校验。

4. **跨文档证据整合能力仍需加强**  
   故障根因分析往往需要综合设备资料、历史案例、现象描述和维修步骤。现有系统在多文档证据整合和上下文组织方面还需优化。

5. **故障诊断评测集仍需建设**  
   当前主要使用通用文档问答数据验证 RAG 能力，后续需要构建面向故障检测任务的标准样例集和人工标注集。
