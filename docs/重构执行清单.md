## 1. 使用方式

这份清单只覆盖**第一阶段实际执行**，目标是收缩 `app/retrievers/local_kb.py`，不混入 `rag.py`、UI、模型替换、评测体系改造等其他任务。

执行时必须遵守三条硬规则：

1. 本阶段只做结构重构，不主动改算法口径
2. 本阶段只拆检索主入口，不顺手改 RAG 编排
3. 每完成一个子步骤，都必须跑对应验证命令

## 4. 第一阶段执行顺序

执行顺序在这里锁定，不允许改成“边想边拆”。

### Step 0：冻结当前回归入口

**动作**

- 先确认下列入口仍作为本阶段回归标准：
  - `python scripts/start_api.py`
  - `python scripts/rebuild_kb.py --kb-name <知识库名>`
  - `python scripts/run_domainrag_local_kb_eval.py ...`
  - `python scripts/run_crud_local_kb_eval.py ...`

**通过标准**

- 后续所有结构调整都沿用这组命令，不再更换入口

### Step 1：先抽出 query profile

**动作**

- 从 `local_kb.py` 中抽出 query 类型识别、query profile 相关逻辑
- 包括普通 query、time-sensitive、comparative、timeseries 相关的识别入口
- `local_kb.py` 改为调用统一的 `query_profile_service`

**目标**

- 以后新增 query 识别逻辑时，不再进入 `local_kb.py`

**这一小步后必须验证**

- API 仍可导入
- `search_local_knowledge_base` 函数签名不变

### Step 2：再抽 candidate retrieval

**动作**

- 从 `local_kb.py` 抽出候选召回相关逻辑
- 包括 dense、BM25、sentence index、timeseries branching 的候选收集
- 新 service 只负责“取候选”，不负责 rerank

**目标**

- 检索召回与后续打分解耦

**这一小步后必须验证**

- Domain / CRUD 本地评测脚本仍能运行到实际检索阶段
- temp KB 检索入口不被破坏

### Step 3：再抽 candidate fusion

**动作**

- 将多路候选融合逻辑从 `local_kb.py` 拆出去
- 让 dense、BM25、timeseries branch 合并逻辑拥有单独入口

**目标**

- 以后改融合策略时，不再碰检索主入口

**这一小步后必须验证**

- 候选列表结构不变
- 现有后续 rerank 调用不需要改 API

#### Step 3 详细执行计划

这一小步按以下顺序执行，不允许再临场调整边界：

1. **先抽候选公共结构**
   - 新增 `candidate_common_service.py`
   - 承接：
     - `RetrievalCandidate`
     - `get_chunk_id`
     - `get_source_modality`
   - 目的：
     - 避免 `candidate_retrieval` 与 `candidate_fusion` 互相引用形成循环依赖

2. **再抽融合分数计算**
   - 新增 `candidate_fusion_service.py`
   - 承接：
     - `apply_candidate_fusion_scores`
     - `build_temporal_candidate_adjustments`
     - `modality_bonus_for_candidate`
     - extension / path bonus
   - 目的：
     - 让 `fused_score` 的形成逻辑从“取候选”动作中剥离出去

3. **再抽多路候选合并**
   - 将下列逻辑收口到 `candidate_fusion_service.py`
     - `merge_retrieval_candidate_lists`
     - `count_candidate_modalities`
   - 目的：
     - 让 dense / lexical / timeseries branch 的合并逻辑不再留在 retrieval service

4. **回改 retrieval service**
   - `candidate_retrieval_service.py` 只保留：
     - dense 候选收集
     - lexical 候选收集
     - sentence index 候选收集
     - timeseries branching 路由
   - 不再保留：
     - `fused_score` 计算细节
     - 候选合并细节
     - 模态 bonus 细节

5. **回改 `local_kb.py` 与评测脚本**
   - `local_kb.py` 只通过 service import 调用 fusion 能力
   - `scripts/eval_retrieval_baselines.py` 同步改到新导入口径

6. **做最小回归**
   - `python -c "from app.retrievers.local_kb import search_local_knowledge_base; print('ok')"`
   - `python -c "from app.api.chat import router; print('chat-ok')"`
   - `python -c "from scripts.eval_retrieval_baselines import parse_args; print('eval-script-ok')"`
   - 三个 retrieval service 文件源码级编译检查

#### Step 3 完成判据

- `candidate_retrieval_service.py` 只剩“取候选”和 branch 路由
- `candidate_fusion_service.py` 独立承接 fusion score 与候选合并
- `candidate_common_service.py` 独立承接候选公共结构
- `local_kb.py` 不再直接内嵌 fusion 细节
- 基线评测脚本导入路径已同步

### Step 4：再抽 candidate rerank

**动作**

- 将 heuristic rerank、model rerank、coverage bonus、diversity bonus 等候选打分逻辑拆出
- 新 service 负责候选排序，不负责 query profile 和候选收集

**目标**

- 让“检索到什么”和“如何排前后”彻底分层

**这一小步后必须验证**

- Domain / CRUD 的评测脚本仍能输出结果
- 返回的 reference 结构不变

### Step 5：最后抽 diagnostics

**动作**

- 将 trace、diagnostics、reference overview 聚合、调试字段拼装等逻辑拆出去
- `local_kb.py` 只保留“调用 diagnostics service 并挂到返回结构”这一步

**目标**

- 调试字段以后扩展时不再把主检索入口撑大

**这一小步后必须验证**

- API `/chat` 相关返回仍可带上原有检索调试信息
- 评测脚本如依赖 diagnostics 字段，不出现字段缺失

### Step 6：收尾瘦身 `local_kb.py`

**动作**

- 删除已经迁移出去的内部实现
- 清理只因拆分而产生的无用 import、局部 helper、重复判断
- 保证 `local_kb.py` 只剩 orchestration 和统一出口

**目标**

- 文件明显缩短
- 新增职责不再继续堆入主入口

**这一小步后必须验证**

- 所有前述验证命令重新跑一遍

## 7. 第一阶段禁止事项

执行这一阶段时，明确禁止以下行为：

- 在拆 `local_kb.py` 的同时改 `rag.py`
- 在拆结构时顺手改排序策略口径
- 因为拆分不方便就修改外部调用签名
- 直接删除现有检索入口函数
- 把 timeseries 语义改掉后说这是“结构重构”
- 顺手清理 `data/eval/` 或归档脚本
