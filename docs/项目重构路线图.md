# 项目重构路线图

> 文档类型：研发执行路线图  
> 版本时间：2026-04-29  
> 适用范围：Mini-Agent-RAG 全项目，后端 `app/` 优先

---

## 1. 重构背景与目标

当前项目已经从“功能能否跑通”阶段进入“功能持续叠加后边界开始模糊”阶段。仓库已经具备本地知识库问答、混合检索、句级索引、多模态加载、增量重建、专项评测等能力，但后端主链路、知识库构建链路、评测脚本和历史产物已经出现结构性膨胀。

从当前仓库体量与职责分布来看，最明显的热点文件包括：

- `app/retrievers/local_kb.py`：约 `111 KB`，是当前最大的主链路热点文件
- `app/chains/rag.py`：约 `52 KB`，是 RAG 编排与特判逻辑集中区
- `app/services/kb/kb_incremental_rebuild.py`：约 `36 KB`，承担了较重的知识库增量重建职责
- `app/loaders/image.py`、`app/ui/app.py` 也偏重，但当前优先级低于后端主链路

这轮重构路线图的目标不是一次性大改，而是明确后续拆分顺序和执行边界。固定目标如下：

- 主链路文件变短，入口文件只保留薄编排职责
- 检索、编排、服务层边界更清楚
- 实验能力从核心路径中解耦
- 知识库构建链路按职责收口
- 评测与过程产物形成明确的生命周期治理

---

## 2. 现状诊断

### 2.1 主链路文件过重

当前 `local_kb.py` 和 `rag.py` 同时承担多种职责，已经不再是单纯的入口文件，而是逐步演变成“总脚本”。  
直接影响是：

- 定位某个低分问题时，很难迅速判断属于召回、排序、上下文还是生成前保护逻辑
- 新能力一旦继续接入，默认就会堆到超大文件里
- 测试与回归难以按层隔离

### 2.2 `service / retriever / chain` 边界混杂

当前仓库已经有 `app/services/README.md` 对 `services` 目录做了 category layout 说明，但真实代码里仍存在边界混杂问题：

- retriever 不只做检索适配，还承担了大量 query 判断、排序控制和诊断逻辑
- chain 不只做编排，还混入了证据组织、保护重试和特殊分支判断
- service 层已经具备分类目录，但还没有完全承接这些被挤压进主链路文件的职责

### 2.3 timeseries 等实验能力侵入主流程

时间序列相关能力已经接入主链路，并且在 `local_kb.py`、`rag.py`、loader 与 summary 层都有分散判断。  
这说明能力本身不是死代码，但结构上已经出现问题：

- 实验能力没有被旁路化
- 功能开关不能完全保证行为隔离
- 文本 RAG 与扩展能力的边界不够清楚

### 2.4 兼容层、正式层、历史产物并存

`app/loaders/documents.py` 当前已经是兼容转发层，但仍在被正式代码引用。  
同时，`scripts/` 下存在多支一次性分析脚本，`data/eval/crud/` 与 `data/eval/phase0/` 下也保留了多版本、分片和历史结果并存的情况。  
这些现象说明仓库正在同时承担：

- 运行系统
- 研究试验场
- 过程留档目录

如果不治理，后续会越来越难分辨“正式入口”和“历史残留”。

### 2.5 `data/eval` 与 `scripts` 缺少生命周期治理

当前已经可以看出几类脚本和产物混放：

- 正式可重复运行的主流程脚本
- 一次性分析脚本
- 分片中间产物
- 历史版本评测结果
- 对外可引用的最终评测文件

它们目前尚未形成统一的保留规则和归档规则，直接影响后续重构时的基线冻结、结果复现和目录可读性。

## 3. 目标结构

### 3.1 总体原则

目标结构按“职责拆分”组织，而不是按“最近在做什么功能”拆分。  
本项目后续的稳定结构应遵循以下分层：

- `api/`：HTTP 路由、请求响应适配、错误处理
- `schemas/`：结构化输入输出、领域数据模型
- `services/core/`：配置、网络、可观测性、运行基础设施
- `services/kb/`：导入、切块、索引、重建
- `services/retrieval/`：query、candidate、rerank、context、diagnostics、timeseries
- `chains/`：RAG 编排，不承担大块策略实现
- `retrievers/`：保留薄适配入口，不继续堆业务策略

### 3.2 目标职责收缩

以下文件在未来结构中应收缩为薄入口：

- `app/retrievers/local_kb.py`
  - 只保留检索 orchestration
  - 不再继续增长 query 判断、候选融合、重排细节、diagnostics 细节

- `app/chains/rag.py`
  - 只保留 RAG 流程编排
  - 不再继续增长上下文组织、证据打包、保护重试、专项扩展判断

- `app/loaders/documents.py`
  - 明确为兼容层
  - 不作为新逻辑入口

### 3.3 目标子系统形态

后端最终建议向以下子系统靠拢：

- `services/retrieval/query/`
  - query 类型识别、rewrite、HyDE、意图抽取
- `services/retrieval/candidate/`
  - dense、BM25、sentence index、多分支候选召回
- `services/retrieval/rerank/`
  - heuristic rerank、model rerank、coverage bonus、diversity bonus
- `services/retrieval/context/`
  - small-to-big、比较类证据拼接、evidence packing
- `services/retrieval/diagnostics/`
  - trace、reference overview、调试信息生成
- `services/retrieval/timeseries/`
  - time series query profile、summary、branching、joint coverage

`services/kb/` 则向以下口径收束：

- `ingestion`
- `chunking`
- `indexing`
- `rebuild`

当前阶段不要求一次性完成目录迁移，但后续实现必须朝这个方向收口。

## 4. 分阶段重构路线

重构顺序在本路线图中锁定，不允许实现者自由调整主顺序。

### Phase 0：冻结边界与建立回归基线

**目标**

- 明确当前稳定 API、关键脚本命令和评测口径
- 固定后续结构重构的回归基线

**实施重点**

- 确认当前主命令仍然视为稳定入口：
  - `python scripts/start_api.py`
  - `python scripts/start_ui.py`
  - `python scripts/rebuild_kb.py --kb-name <name>`
  - `python scripts/run_domainrag_local_kb_eval.py ...`
  - `python scripts/run_crud_local_kb_eval.py ...`
- 固定 Domain / CRUD 当前关键回归文件与样例集
- 明确哪些脚本是正式保留、哪些只是过程工具

**完成判据**

- 后续每个阶段都能沿用同一组回归入口
- 重构不再伴随“顺手换命令、顺手换评测口径”

### Phase 1：收缩检索主入口

**目标**

从 `app/retrievers/local_kb.py` 拆出独立职责，让该文件退化为薄 orchestration。

**必须拆出的职责**

- query profile
- candidate retrieval
- candidate fusion
- rerank
- diagnostics

**完成形态**

- `local_kb.py` 只负责流程串联和统一返回结构
- 新增逻辑不再直接写入 `local_kb.py`

**退出条件**

- API 与评测脚本对 `search_local_knowledge_base` 的调用方式保持稳定
- Domain / CRUD 检索结果口径可复测

### Phase 2：收缩 RAG 编排主入口

**目标**

从 `app/chains/rag.py` 中拆出证据组织与保护逻辑，使其收缩为流程编排器。

**必须拆出的职责**

- context build
- evidence packing
- answer guard / completeness retry
- runtime orchestration helper

**完成形态**

- `rag.py` 主要保留 `generate_rag_answer` / `stream_rag_answer` 等入口编排
- 专项保护逻辑不再继续堆积在同一文件内

**退出条件**

- `/chat/rag` 行为不破
- Agent 调用 RAG 链路不破
- 典型 bad case 回放口径可保持一致

### Phase 3：收口知识库构建链路

**目标**

将 `services/kb/` 层按 `ingestion / chunking / indexing / rebuild` 口径收束。

**重点处理**

- `kb_incremental_rebuild.py`
- `kb_ingestion_service.py`
- `embedding_assembler.py`
- sentence index 相关入口

**完成形态**

- 全量重建与增量重建边界更清楚
- 导入、切块、索引、重建各自有明确承载位置

**退出条件**

- 当前全量重建脚本仍可跑
- 当前增量重建链路仍可跑
- 知识库导入与重建错误更容易按层定位

### Phase 4：实验能力与扩展能力旁路化

**目标**

将 timeseries 等扩展能力从主流程散点判断收拢成独立扩展能力。

**重点处理**

- query profile 中的 timeseries 判断
- retrieval branching 中的 timeseries 路径
- RAG chain 中的 timeseries joint coverage 与相关 guard

**完成形态**

- 文本 RAG 主链路和扩展能力边界清楚
- 功能开关能真正控制行为
- 扩展能力能被单独测试和回归

**退出条件**

- timeseries 关闭时，主文本链路不受污染
- timeseries 开启时，专项能力仍可运行

### Phase 5：脚本与评测产物治理

**目标**

对 `scripts/` 和 `data/eval/` 建立正式保留规则与归档规则。

**重点处理**

- 区分保留脚本、归档脚本、一次性分析脚本
- 区分正式评测结果、分片中间产物、历史版本产物
- 清理“总结果 + 分片结果 + 旧版结果”长期并列无说明的情况

**完成形态**

- 仓库结构更适合作为长期维护项目，而不是研究过程堆栈
- 执行者能快速找到正式入口和正式报告文件

**退出条件**

- README 与 docs 可准确指向正式脚本与正式结果
- 归档与保留规则形成文档化说明

### 暂不优先处理的方向

为避免重构失焦，以下事项明确不在当前主路线前列：

- UI 重构
- 图像链路深拆
- 新模型替换
- 新评测体系扩展

## 5. 模块级改造指引

### 5.1 `retrievers/local_kb.py`

**当前职责**

- query 分析
- 候选召回
- timeseries 分支控制
- sentence index 使用判定
- rerank
- diagnostics
- reference overview 输出

**目标职责**

- 仅保留检索流程编排和统一结果出口

**不该继续放进去的逻辑**

- 新的 query 类型判断
- 新的候选打分规则
- 新的实验性分支控制
- 新的 trace 细节拼装

### 5.2 `chains/rag.py`

**当前职责**

- 检索后 RAG 编排
- context group 与 reference summary
- 比较类与 timeseries 特判
- completeness retry 与 answer guard

**目标职责**

- 只保留问答流程编排与少量入口判断

**不该继续放进去的逻辑**

- 大段上下文拼接算法
- 扩展能力专项覆盖判断
- 复杂保护逻辑实现细节

### 5.3 `services/kb/`

**当前职责**

- 导入、组装、索引、重建职责已基本存在，但边界不够稳定

**目标职责**

- ingestion：文件进入系统
- chunking：切块与 chunk metadata
- indexing：向量、BM25、sentence index
- rebuild：全量与增量编排

**不该继续放进去的逻辑**

- 与检索策略直接相关的实验逻辑
- 与 UI 呈现耦合的行为

### 5.4 `loaders/`

**当前职责**

- 多模态内容加载
- 兼容层保留

**目标职责**

- 各类型 loader 独立
- `documents.py` 只承担兼容导出

**不该继续放进去的逻辑**

- 业务策略判断
- 与知识库重建编排强耦合的流程逻辑

### 5.5 `scripts/`

**当前职责**

- 正式入口脚本与过程分析脚本混放

**目标职责**

- 保留可复现主脚本
- 一次性分析脚本明确归档

**不该继续放进去的逻辑**

- 无说明的临时复现实验脚本长期留在根层

### 5.6 `data/eval/`

**当前职责**

- 正式报告文件、样本、分片产物、历史版本并存

**目标职责**

- 最终结果、输入样本、中间分片、历史归档分层

**不该继续放进去的逻辑**

- 无生命周期说明的重复结果长期堆积

## 6. 阶段验收与退出条件

每一阶段都必须满足以下通用要求：

### 6.1 进入条件

- 上一阶段的回归入口已经冻结
- 本阶段目标只涉及结构调整，不混入无关算法变化
- 已知依赖点和兼容点已列清

### 6.2 完成判据

- 主命令仍可运行
- API 不破
- 评测脚本不破
- Domain / CRUD 的关键口径可复测
- 新目录与新职责边界有明确承接位置

### 6.3 不通过时的回退方式

- 回退到上阶段稳定入口文件
- 保留兼容层，不强拆调用方
- 结构重构与行为变化拆分提交，不混在一次回退里

### 6.4 强制回归项

每阶段结束时至少复核：

- 主 API smoke test
- 知识库重建 smoke test
- Domain 检索回归
- CRUD 闭环稳定性回归

---

## 7. 结论

本路线图的核心不是追求一次性“把目录改漂亮”，而是把当前项目从“主链路不断变厚、实验逻辑不断内嵌、历史产物不断堆积”的状态，逐步拉回到一个可以长期维护、可以稳定做实验、可以清楚解释结果来源的工程形态。

后续所有具体重构动作，都应严格服从本路线图的阶段顺序：先建基线，再拆检索入口，再拆 RAG 编排，再收口知识库，再旁路扩展能力，最后治理脚本与产物。
