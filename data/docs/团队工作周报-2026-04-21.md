## 二、与上周对比

### 1. 工作阶段的变化

- 上周重点是：把官方 `CRUD_RAG` 数据集和本地知识库链路接通，让系统“能评、能跑、能出结果”。
- 本周重点是：在此基础上继续把评测做深、把优化做细，开始回答“为什么这类题排不上去、为什么这类题块不够准、下一步该先改哪里”。

### 2. 评测范围的变化

- 上周主要以 `CRUD` 官方评测、小批量 `RAGAS` 为主，重点验证链路是否稳定。
- 本周新增了：
  - `CRUD + Domain` 综合对比
  - `Domain 100` 检索评测
  - reranker 单模型对比
  - 按题型路由 reranker
  - `Phase 0` 人工集与 bad case 分桶

### 3. 问题定位粒度的变化

- 上周的判断更偏宏观：
  - “材料大多能找到”
  - “事实正确率还不够高”
- 本周已经能进一步拆成更具体的问题类型：
  - `low_rank`
  - `chunk_noise`
  - `cross_passage`
  - 以及不同题型对应的 reranker 差异

### 4. 技术路线的变化

- 上周主要新增的是通用型能力：
  - `Multi-Query`
  - `HyDE`
  - `BM25` 持久化
  - `Corrective RAG`
  - 同题文档优先排序
- 本周的路线更偏“精细化优化”：
  - 时间敏感检索优化
  - 多文档证据覆盖优化
  - reranker 模型对比
  - 按 query type 路由 reranker
  - `Phase 0` 小而准人工集

  - 但可以明确看出：项目重心已经从“先把召回和链路跑通”转向“继续提升排序质量和证据命中质量”

### 6. 当前阶段结论

- 相比上周，本周最大的进步不是“又多接了一个模块”，而是：
  - 评测闭环更完整了
  - 问题类型更清楚了
  - 排序优化已经有稳定收益了
  - 后续优化不再靠感觉，而是开始基于人工集和分桶结果推进

### 本周新增 RAG 技术与效果

### 1. 时间敏感检索优化

- **技术说明**：围绕 `time-sensitive_qa`，在检索链路中补充时间意图识别、时间约束保护、日期 metadata 进入 chunk、时间排序加权等能力，尽量减少“问题问的是某个时间点，但系统找到的是别的年份版本”的情况。
- **本周效果**：
  - 时间敏感检索链路已完成多轮“一改一测”，其中保留下来的有效改动主要包括：
    - 时间意图识别
    - 查询改写中的时间约束保护
    - `date` metadata 进入 chunk metadata 并参与排序
  - 当前这类问题仍然是 `Domain` 中最薄弱的一类，但已经从“明显失稳”转为“可继续精修”的状态。

### 2. 多文档证据覆盖优化

- **技术说明**：针对 `multi-doc_qa`，不是继续单纯提高召回，而是让前排候选尽量覆盖不同来源、不同文档家族，减少同一来源连续占位。
- **本周效果**：
  - 当前 `multi-doc_qa` 在 routed reranker 方案下已恢复到较稳定状态：
    - `MRR = 0.9750`
    - `NDCG@5 = 0.8389`
  - 说明多文档问题当前的主要短板已经从“检索不到”转向“生成阶段如何更完整地整合多个证据”。

### 3. Reranker 模型对比与按题型路由

- **技术说明**：
  - 先在同一套 `Domain 100` 上只替换 `RERANK_MODEL`，对比 `bge-reranker-base` 与 `bge-reranker-v2-m3`；
  - 再基于实验结果，按 query type 路由 reranker，而不是所有题都使用同一个模型。
- **本周效果**：
  - 单模型对比显示：
    - `v2-m3` 在 `extractive_qa / structured_qa` 上更强
    - `base` 在 `multi-doc_qa / time-sensitive_qa` 上更稳
  - 路由方案保留到主链路后，当前 `Domain 100` 稳定结果为：
    - `Recall@5 = 0.8700`
    - `MRR = 0.7410`
    - `NDCG@5 = 0.7445`
    - `Top1 Hit = 0.6700`
  - 这也是当前阶段最稳的一版组合。

### 4. Phase 0 人工集与 Bad Case 分桶

- **技术说明**：在继续优化前，先建立一套“小而准”的人工 gold 集，固定评测口径，并把失败样本按问题类型拆成可解释的 bucket，避免后续优化被代理指标误导。
- **本周效果**：
  - 第一版种子集已扩充到 `20` 条，并统一加入：
    - `review_status`
    - `history_qa`
    - `gold_documents`
    - `gold_passages`
    - `answerable_from_single_chunk`
    - `failure_bucket`
  - 首轮分桶结果为：
    - `chunk_noise = 4`
    - `low_rank = 6`
    - `cross_passage = 8`
    - `missed_recall = 0`
  - 当前结论非常明确：这批样本里主要问题已经不是“召回不到”，而是“排不上去、返回块不够准、跨段整合不够强”。

### 5. 句级索引基础设施

- **技术说明**：不是把主检索全改成句级，而是先补一套句级副索引，为后续“双层索引”方案做工程准备。
- **本周效果**：
  - 句级索引服务已落地，知识库重建流程已支持自动构建句级副索引。
  - 当前句级索引主要承担“句提示辅助 rerank”的作用，尚未直接作为默认主检索入口。
  - 这部分属于后续真正实施“双层索引”优化的基础设施准备。

### 技术效果总结

1. **检索稳定性**：当前系统已经形成了“混合检索 + rerank + 分题型 reranker 路由”的稳定主链路，整体排序质量比本周初更强。
2. **主要收益点**：本周最明确的收益来自 reranker 对比与 reranker 路由，而不是继续增加召回数量。
3. **问题定位能力**：`Phase 0` 人工集和 bad case 分桶已经让问题从“感觉哪里不对”变成“能明确指出是哪一类失败”。
4. **后续优化方向**：下一阶段更值得做的是 `low_rank / chunk_noise / cross_passage` 三类定向优化，而不是继续粗放地调大候选数或增加更多通用模块。

## 四、当前问题

1. 当前 `Domain` 检索整体已经较强，但 `Top1` 命中仍不够稳，说明正确文档常常能进前列，却还不能稳定排到第一。
2. `chunk_noise` 问题仍比较突出，表现为“文档对了，但返回块没有直接承载答案句”，这会同时影响检索解释性和生成质量。
3. `cross_passage` 仍然是结构性短板，尤其在 `multi-doc_qa` 和 `CRUD cross-passage` 样本上更明显。
4. 当前 `Phase 0` 人工集还未覆盖 `OCR / image evidence`，因此这部分问题的评测闭环仍不完整。
5. 一些时间敏感样本本身带有隐含时间锚点，说明后续还需要进一步区分“真实排序失败”和“样本本身依赖隐藏上下文”两类情况。
